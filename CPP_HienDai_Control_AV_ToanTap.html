PHẦN 0 — VÌ SAO C++ CHO CONTROL & AV

Bối cảnh ngành + thiết lập môi trường biên dịch trước khi viết code

📌 Tại sao AV dùng C++?

Ba lý do kỹ thuật cụ thể, không phải sở thích:

  • Real-time & deterministic: vòng điều khiển phải chạy đúng chu kỳ (vd 100Hz) trên phần cứng có hạn. C++ không có garbage collector chạy ngầm như Python/Java — bạn kiểm soát hoàn toàn khi nào cấp/giải phóng bộ nhớ → độ trễ ổn định.
  • Hiệu suất: điều khiển MPC/NMPC cần giải bài toán tối ưu trong vài mili-giây. Python mất ~10–100× thời gian cho cùng thuật toán.
  • Tiếp cận phần cứng: đọc encoder/CAN, điều khiển động cơ, cấu hình bộ đếm — tất cả qua driver cấp thấp viết bằng C/C++.
⚖️ C vs C++: vì sao chọn C++ cho phần điều khiển cấp cao

C = "con dao gọt bút chì" — gần phần cứng nhất, dùng cho firmware thuần (bootloader, driver). C++ = "hộp công cụ" — vẫn đủ nhanh như C nhưng có thêm OOP, STL, RAII giúp viết thuật toán phức tạp (planner, MPC) sạch và an toàn hơn. Trong AV: firmware/tầng driver dùng C, tầng planning/control dùng C++.

🔎 Ẩn dụ xuyên suốt: C++ là "nhà máy sản xuất mô-đun"

PHẦN 1 — NỀN TẢNG: BIẾN, CON TRỎ, THAM CHIẾU, CONST

Những khác biệt gây "sốc văn hóa" khi chuyển từ Python/Matlab sang C++

📌 Kiểu dữ liệu & auto

C++ là ngôn ngữ tĩnh định kiểu (statically typed): kiểu biến được xác định lúc biên dịch. Khác hẳn Python — nếu gán sai kiểu, compiler báo lỗi trước khi chạy, đó là tính năng bảo vệ bạn, không phải phiền phức.

int    n = 5;              // số nguyên 32-bit
double x = 1.2345;         // số thực 64-bit — DÙNG cho control
bool   ok = true;
float  f = 1.0f;           // 32-bit — hiếm dùng, thiếu chính xác

// Từ C++11: auto — compiler tự suy kiểu từ giá trị
auto a = 3.14;             // a: double
auto b = 5;                // b: int
auto v = std::vector<double>{1,2,3}; // v: vector<double>

Quy tắc control: mọi số trong vòng điều khiển dùng double. float dành cho lưu lượng/động cơ nơi cần tiết kiệm bộ nhớ. Vì sao? Sai số làm tròn float (~$10^{-7}$) tích lũy qua nghìn vòng lặp sẽ phá chất lượng bám.

📌 Con trỏ (pointer) — biến "chỉ đường"

Con trỏ lưu địa chỉ bộ nhớ của một biến khác. Dùng toán tử & để lấy địa chỉ, * để truy cập giá trị tại địa chỉ đó (dereference).

double x = 1.5;
double* ptr = &x;   // ptr trỏ tới địa chỉ của x
*ptr = 2.5;          // ghi 2.5 vào x qua con trỏ
// x bây giờ là 2.5

Vì sao cần con trỏ trong control? Vì dữ liệu lớn (ma trận, điểm cloud, ảnh) không nên copy mỗi lần truyền hàm — copy 100.000 điểm mỗi chu kỳ = lãng phí thời gian real-time. Con trỏ cho phép hàm "nhìn vào" cùng một vùng nhớ.

⚠️ Null pointer — con trỏ "không trỏ đâu cả"

Con trỏ có thể bằng nullptr (C++11, thay cho NULL của C). Dereference nullptr là crash tức thì. Luôn kiểm tra trước khi dùng:

double* p = nullptr;
if (p != nullptr) { *p = 0.0; }  // an toàn
// *p = 0.0;  // CRASH — p không trỏ tới gì

Trong code C++ hiện đại, bạn ít khi phải dùng con trỏ thô (raw pointer) cho sở hữu tài nguyên — đó là việc của smart pointer (Phần 3). Con trỏ thô chỉ dùng khi "mượn nhìn" dữ liệu không sở hữu.

📌 Tham chiếu (reference) — "bí danh" của biến

Tham chiếu là một tên khác cho cùng biến. Khác con trỏ ở 2 điểm: không thể là nullptr (luôn trỏ tới đối tượng hợp lệ), và không cần * để truy cập.

double x = 1.5;
double& ref = x;   // ref là bí danh của x
ref = 2.5;          // x = 2.5

void update_velocity(double& v) { v += 0.1; }  // sửa TRỰC TIẾP v

Quy tắc vàng trong control: truyền tham số vào hàm bằng const reference (đọc nhanh, không copy, không sửa được), truyền tham số cần sửa bằng reference thường.

double norm(const std::vector<double>& v);  // đọc mà không copy
void  saturate(double& u, double u_max);      // sửa u tại chỗ
📌 const — lời hứa không sửa đổi

const báo compiler "đây là hằng, không được sửa". Compiler sẽ báo lỗi nếu bạn vô tình gán giá trị mới — phát hiện lỗi logic từ lúc biên dịch, đặc biệt quan trọng với các hằng số vật lý.

const double k = 2.0;   // hằng số điều khiển
const double GRAVITY = 9.81;
k = 3.0;                 // ❌ LỖI BIÊN DỊCH

// Hàm chỉ đọc dữ liệu → khai báo const để ép an toàn
void print(const std::vector<double>& v) {
    // v.push_back(1.0); // ❌ không biên dịch được
}

Trong môi trường code lớn (ROS2, Autoware), const đúng chỗ là "hợp đồng" giữa các module — đọc code người khác an tâm hơn rất nhiều.

BT1.1 Gõ chương trình sau, chạy, rồi sửa lại để in ra kết quả đúng như ghi chú: 
#include <iostream>

int main() {
    double x = 1.5;
    double& r = x;     // r là bí danh của x
    r = 3.0;           // x bây giờ là bao nhiêu?

    return 0;
}
✅ Đáp án

In ra x = 3. Vì r là bí danh của x, gán r = 3.0 đồng nghĩa gán cho x. Đây là cách tham chiếu "nhìn thấy" cùng biến — không có bản sao.

BT1.2 Gõ, đoán kết quả, rồi chạy: 
#include <iostream>

void f(double x)  { x = 10.0; }   // truyền giá trị
void g(double& x) { x = 10.0; }   // truyền tham chiếu
void h(const double& x) { /* x = 10.0; */ }  // thử bỏ comment xem lỗi gì

int main() {
    double a = 1.0, b = 1.0;
    f(a);  g(b);
    std::cout << "a = " << a << ", b = " << b << "\n";
    return 0;
}
✅ Đáp án

In ra a = 1, b = 10. f sửa bản sao (không đổi a); g sửa trực tiếp (đổi b). Bỏ comment trong h → lỗi biên dịch vì const cấm sửa. Đây là lý do const reference được dùng khi chỉ muốn đọc.

PHẦN 2 — CLASS & OOP

Encapsulation, Inheritance, Polymorphism — 3 trụ cột tổ chức code robot

📌 Class — khuôn mẫu "đối tượng"

Class gom dữ liệu (thành viên) + hành vi (phương thức) thành một đơn vị. Trong AV, mỗi class là một module: Controller, KalmanFilter, MotorDriver, Planner.

#include <iostream>
#include <cmath>

class LQRController {
private:                 // chỉ code bên trong class dùng được
    double q_;            // trọng số Q
    double r_;            // trọng số R
    double k_;            // hệ số phản hồi K (tính từ ARE)
public:                  // ai cũng dùng được — "cửa sổ"
    LQRController(double q, double r) : q_(q), r_(r) {
        // nghiệm ARE cho hệ bậc 1: k = q + sqrt(q*q + q*r) ... (bài tập)
    }

    void setK(double k) { k_ = k; }

    // tính tín hiệu điều khiển từ trạng thái
    double compute(double x) const { return -k_ * x; }
};

int main() {
    LQRController c(3.0, 1.0);
    double u = c.compute(0.5);   // u = -k * 0.5
    std::cout << "u = " << u << "\n";
    return 0;
}

Ba điều mới so với Python:

  • private/public: kiểm soát truy cập (encapsulation) — chặn lỗi sửa nhầm từ ngoài.
  • Constructor LQRController(...): hàm chạy khi tạo đối tượng, thường khởi tạo thành viên qua initializer list : q_(q), r_(r) (đúng chuẩn C++, không gán trong thân hàm).
  • Member initializer list dùng dấu hai chấm sau tên constructor — bắt buộc quen vì tài liệu thật đều viết thế.

💪 Luyện tập Phần 2a — Class cơ bản

BT2.1 Gõ class Integrator — tích phân số Euler $\int u\,dt$ gần đúng bằng $y_{k+1} = y_k + u_k T_s$: 
#include <iostream>

class Integrator {
private:
    double y_;
    double ts_;
public:
    Integrator(double ts) : y_(0.0), ts_(ts) {}   // initializer list
    void reset() { y_ = 0.0; }
    double step(double u) {
        y_ += u * ts_;
        return y_;
    }
};

int main() {
    Integrator intg(0.1);
    std::cout << intg.step(2.0) << "\n";   // 0.2
    std::cout << intg.step(2.0) << "\n";   // 0.4
    return 0;
}
✅ Đáp án

Chạy được, in 0.2 rồi 0.4. Mỗi lần gọi step, y tăng thêm u×0.1. Hãy thử đổi ts_ thành 0.05 → các giá trị in ra thành 0.1, 0.2 — đó là tích phân chậm hơn. Đây chính là khâu tích phân của PID bạn đã học trong tài liệu PID.

BT2.2 Thêm phương thức get() vào Integrator để đọc giá trị hiện tại mà không thay đổi đối tượng (đánh dấu const): 
double get() const { return y_; }   // const: hứa không sửa đổi
✅ Đáp án

Thêm vào phần public của class. Gọi intg.get() trả về y mà không cần step. Chữ const ở cuối là "hợp đồng" với compiler: phương thức này không sửa thành viên — gọi được cả trên đối tượng const. Đây là phong cách bắt buộc trong code chuyên nghiệp.

🎯 Tổ chức file chuẩn công nghiệp

Mỗi class một cặp file: header (.h) khai báo interface (public/private), source (.cpp) viết thân hàm. Compiler cần thấy header, linker ráp source:

📌 Inheritance (kế thừa) — mở rộng mà không phá code cũ

Kế thừa cho phép class mới (Derived) thừa hưởng và mở rộng class cũ (Base). Trong AV: BaseController → PIDController, LQRController, MPCController.

class Controller {            // base
public:
    virtual ~Controller() = default;
    virtual double compute(double x) const = 0;  // pure virtual
};

class PIDController : public Controller {
public:
    double compute(double x) const override { return -kp_ * x; }
private:
    double kp_ = 1.0;
};

class LQRController : public Controller {
public:
    double compute(double x) const override { return -k_ * x; }
private:
    double k_ = 2.0;
};

void run(Controller& c, double x) { double u = c.compute(x); }
📌 Polymorphism & virtual — "một hợp đồng, nhiều triển khai"

Từ khóa virtual + override tạo đa hình (polymorphism): bạn gọi compute() qua con trỏ/reference của Controller, nhưng đúng phiên bản PID hay LQR được chạy tùy đối tượng thật. Đây là cách viết Controller cho bộ điều khiển mà không cần sửa code gọi.

  • = 0 sau khai báo = pure virtual — class đó không thể tạo đối tượng trực tiếp (interface).
  • override (C++11): bắt compiler kiểm tra bạn ghi đè đúng chữ ký.
  • virtual ~Controller() = default; — bắt buộc: nếu không, khi hủy qua con trỏ base, destructor của Derived không chạy → rò rỉ tài nguyên.
⚠️ Quy tắc "hướng đối tượng thực dụng" cho người làm control

Đừng lạm dụng kế thừa sâu 5 cấp như giáo trình IT. Trong control: 1 cấp interface + vài class triển khai là đủ. Nếu cần thay đổi hành vi, ưu tiên composition (đối tượng chứa đối tượng) hơn kế thừa. Đọc code Autoware/F1TENTH để thấy sự thực dụng này.

💪 Luyện tập Phần 2b — Inheritance & Polymorphism

BT2.3 Gõ lại ví dụ Controller ở trên, thêm class MPCController cũng kế thừa Controller với công thức $u = -5x$: 
#include <iostream>

class Controller {
public:
    virtual ~Controller() = default;
    virtual double compute(double x) const = 0;
};

class PIDController : public Controller {
public:
    double compute(double x) const override { return -1.0 * x; }
};

class LQRController : public Controller {
public:
    double compute(double x) const override { return -2.0 * x; }
};

class MPCController : public Controller {
public:
    double compute(double x) const override { return -5.0 * x; }
};

int main() {
    PIDController  pid;
    LQRController  lqr;
    MPCController  mpc;
    Controller& c1 = pid;   // đa hình: gọi qua reference base
    Controller& c2 = lqr;
    Controller& c3 = mpc;
    std::cout << c1.compute(1.0) << " " << c2.compute(1.0) << " "
              << c3.compute(1.0) << "\n";   // -1 -2 -5
    return 0;
}
✅ Đáp án

In ra -1 -2 -5. Cùng một lời gọi compute(1.0) qua kiểu Controller& nhưng mỗi đối tượng thật chạy phiên bản riêng — đó là polymorphism. Hãy thử viết hàm void run(Controller& c, double x) gọi chung 3 bộ điều khiển mà không cần biết loại.

BT2.4 Viết class WheelEncoder mô phỏng encoder: có tick() tăng bộ đếm, getPosition() trả về vị trí = bộ đếm × khoảng cách mỗi tick. Khởi tạo với meters_per_tick = 0.05. Gõ 10 tick → in vị trí.
✅ Đáp án 
class WheelEncoder {
public:
    explicit WheelEncoder(double mpt) : mpt_(mpt), cnt_(0) {}
    void tick() { ++cnt_; }
    double getPosition() const { return cnt_ * mpt_; }
private:
    double mpt_;
    int    cnt_;
};
// main: tạo enc(0.05), gọi tick() 10 lần → getPosition() = 0.5

Đây là mô hình gần thật của đồ án STM32 odometry: đếm xung encoder rồi nhân hệ số. explicit trước constructor chặn tự động ép kiểu — thói quen tốt nên tập ngay.

PHẦN 3 — RAII & SMART POINTER

Chống rò rỉ bộ nhớ — kỹ năng sống còn của code real-time

📌 Vấn đề: bộ nhớ heap phải tự giải phóng

Bạn cấp vùng nhớ động bằng new, và phải delete khi xong. Quên delete → rò rỉ bộ nhớ: sau vài giờ robot chạy, RAM cạn → crash giữa đường. Đây là lỗi kinh điển của C (và C++ cũ).

double* data = new double[1000];  // cấp vùng nhớ
// ... dùng data ...
// Quên: delete[] data;  → RÒ RỈ 8KB mỗi chu kỳ

Trong vòng điều khiển chạy 100Hz, rò 8KB/lần = 800KB/s → sau 1 giờ đã hết hàng trăm MB. Với Python bạn không lo vì có garbage collector; với C++ bạn phải lo — và giải pháp không phải "nhớ delete" mà là RAII.

🏛️ RAII — Resource Acquisition Is Initialization

Ý tưởng: tài nguyên (bộ nhớ, file, lock, kết nối CAN) được cấp trong constructor của một đối tượng và giải phóng trong destructor của đúng đối tượng đó. Khi đối tượng ra khỏi phạm vi (scope), destructor tự động chạy — dù là thoát bình thường hay gặp exception. Không thể quên, không thể rò rỉ.

{
    std::ifstream file("log.csv");   // RAII: mở file
    // ... đọc file ...
}   // khi ra khỏi { }: file TỰ ĐÓNG — không cần gọi close()

Nguyên tắc này không chỉ cho bộ nhớ: mọi tài nguyên đều nên bọc trong đối tượng RAII. C++ toàn tập vận hành trên nguyên lý này.

📌 std::unique_ptr — "sở hữu duy nhất"

std::unique_ptr<T> là con trỏ sở hữu duy nhất một đối tượng. Không thể copy — chỉ có đúng một chủ. Khi nó bị hủy, đối tượng bị hủy theo.

#include <memory>
auto c = std::make_unique<LQRController>(3.0, 1.0);  // C++14
double u = c->compute(0.5);   // truy cập qua ->
// Không cần delete — khi c ra khỏi scope, tự giải phóng

// std::make_unique<T> là cách chuẩn (không dùng new trực tiếp)
// → tránh lỗi nếu exception xảy ra giữa cấp phát và gán
📌 std::shared_ptr — "nhiều chủ sở hữu"

std::shared_ptr<T> dùng đếm tham chiếu: nhiều con trỏ chia sẻ một đối tượng; đối tượng chỉ bị hủy khi con trỏ cuối cùng bị hủy. Dùng khi nhiều module cùng dùng chung dữ liệu (vd thông tin bản đồ cho cả planner lẫn localizer).

auto map = std::make_shared<GridMap>();
planner.use(map);      // copy shared_ptr: đếm = 2
localizer.use(map);    // copy shared_ptr: đếm = 3
// khi planner và localizer hủy → đếm = 1 → map vẫn sống
// khi biến map gốc hủy → đếm = 0 → GridMap bị hủy an toàn
⚠️ 2 cạm bẫy phỏng vấn thường hỏi
  • Vòng tham chiếu (circular reference): A sở hữu shared_ptr tới B, B sở hữu shared_ptr tới A → đếm không bao giờ về 0 → rò rỉ. Giải pháp: một bên dùng std::weak_ptr (con trỏ "quan sát", không giữ đối tượng sống).
  • Nên dùng gì: mặc định unique_ptr. Chỉ dùng shared_ptr khi thực sự cần chia sẻ sở hữu. shared_ptr có chi phí (đếm tham chiếu) — trong vòng lặp real-time, ưu tiên truyền bằng reference, không tạo shared_ptr liên tục.
🔎 Ẩn dụ: khóa khách sạn

unique_ptr = chìa khóa phòng duy nhất — chỉ một người có, khi người đó rời khách sạn thì dọn phòng. shared_ptr = thẻ nhóm vào chung cư — nhiều người có thẻ, khi người cuối cùng rời đi mới đóng cổng. weak_ptr = thẻ khách — được vào khi cổng còn mở, nhưng không giữ cổng mở.

BT3.1 Gõ chương trình dùng unique_ptr để tự động quản lý một đối tượng động, kèm 1 class nhỏ in lúc hủy để thấy destructor chạy:

In theo thứ tự: Buffer created → dang dung buffer → Buffer DESTROYED → xong. Quan sát: destructor tự chạy khi b ra khỏi phạm vi {}. Nếu không có unique_ptr, bạn phải nhớ delete — và khi gặp exception ở giữa, delete không chạy → rò rỉ. RAII đảm bảo destructor luôn chạy dù có exception.

PHẦN 5 — TEMPLATE & LAMBDA

Hai cú pháp khiến người mới "sốc" nhất C++; phần này đi từng bước nhỏ, không bỏ qua bất cứ dấu ngoặc nào

🎯 Trước khi bắt đầu — bạn cần biết gì

Phần này chỉ cần bạn nắm vững 3 thứ đã học: (1) hàm thường trong C++ (kiểu trả về + tên + tham số), (2) std::vector, (3) con trỏ/tham chiếu. Template và lambda không phải kiến thức mới lạ hoàn toàn — chúng là "cách viết ngắn lại" của những thứ bạn đã biết. Nếu đọc tới đâu vướng, hãy dừng và làm bài nhỏ ở cuối mỗi đoạn trước khi đọc tiếp.

5.1 — Template là gì? Vì sao phải có nó?

🔎 Bắt đầu bằng vấn đề thực tế (đừng nhảy vào cú pháp vội)

Bạn cần một hàm tính bình phương. Viết thường:

double square_d(double x) { return x * x; }
int    square_i(int    x) { return x * x; }
float  square_f(float  x) { return x * x; }

Ba hàm làm y hệt nhau, chỉ khác kiểu dữ liệu. Trong control thực tế bạn gặp liên tục: lọc EMA, tích phân, khâu trễ — đều cần chạy cho cả double (đo đạc) lẫn int (bộ đếm). Viết 3 bản thì dài, dễ sửa sót 1 chỗ.

Template là câu trả lời: viết một lần, "đúc" ra bao nhiêu bản tùy thích. Giống cái khuôn bánh: bạn có một cái khuôn, đổ bột gì cũng ra bánh cùng hình — đổ bột đậu (double) hay bột gạo (int) đều được, nhưng bánh ra đúng loại bột bạn đổ vào.

📌 Cú pháp template hàm — từng thành phần 
template <typename T>      // dòng 1: khai báo "có 1 kiểu tên là T"
T square(T x) {            // dòng 2: như hàm thường, nhưng T là "kiểu bất kỳ"
    return x * x;
}

Đọc chậm từng dòng:

  • template — từ khóa báo compiler "đây là khuôn, đừng biên dịch ngay".
  • <typename T> — trong ngoặc nhọn là danh sách "kiểu chưa xác định". Ở đây chỉ có một, đặt tên là T (tùy ý, nhưng quy ước dùng T cho "Type"). typename giống "chỗ trống để điền tên kiểu".
  • T square(T x) — chữ T đầu tiên là kiểu trả về, chữ T x là tham số. Tức là: "kiểu trả về giống kiểu của tham số, và tôi chưa nói là kiểu gì".

Khi bạn gọi hàm, compiler mới "điền" T vào:

double a = square(2.5);   // T = double → compiler tự tạo hàm "bản double"
int    b = square(3);     // T = int    → compiler tự tạo hàm "bản int"

Điểm quan trọng nhất: square không hề tồn tại trong file chạy — compiler chỉ tạo ra 2 bản riêng biệt square(double) và square(int) sau khi biết bạn gọi kiểu nào. Có thể kiểm chứng bằng lệnh nm square.o | grep square — bạn sẽ thấy 2 ký hiệu khác nhau.

✅ Đáp án

Bản float: square(float). Vì đối số 3.14f có kiểu float, compiler suy T = float. Nếu bạn viết 3.14 (không có chữ f), nó là double → T = double.

Không. T = const char* (chuỗi ký tự), nhưng trong thân hàm có x * x — con trỏ không có phép nhân → compiler báo lỗi. Lỗi template thường dài dòng khó đọc, nhưng hãy đọc dòng cuối cùng: nó luôn nói rõ dòng nào trong hàm bạn gây lỗi.

5.2 — Class template (một bậc nữa)

📌 Template áp dụng cho class — bộ lọc EMA

Bạn đã biết bộ lọc EMA từ tài liệu Kalman/IMU: $y_k = \alpha x_k + (1-\alpha) y_{k-1}$. Viết class thường chỉ dùng cho double:

class EMA {
    double alpha_;
    double prev_;
public:
    EMA(double a) : alpha_(a), prev_(0.0) {}
    double update(double x) {
        prev_ = alpha_ * x + (1 - alpha_) * prev_;
        return prev_;
    }
};

Giờ muốn dùng cho float (để tiết kiệm bộ nhớ trên vi điều khiển)? Chỉ cần "khuôn hóa" double thành T:

template <typename T>              // thêm dòng này lên đầu class
class EMA {
    T alpha_;
    T prev_;
public:
    EMA(T a) : alpha_(a), prev_(T(0)) {}
    T update(T x) {
        prev_ = alpha_ * x + (1 - alpha_) * prev_;
        return prev_;
    }
};

Dùng như một class thường, nhưng phải nói rõ kiểu trong ngoặc nhọn khi tạo đối tượng (compiler không tự suy được kiểu cho class):

EMA<double> filt1(0.9);   // bản double — cho máy tính lớn
EMA<float>  filt2(0.9f);  // bản float  — cho STM32, tiết kiệm RAM

double y1 = filt1.update(3.0);
float  y2 = filt2.update(3.0f);

Khác biệt so với template hàm: hàm tự suy T từ đối số; class thì phải ghi EMA<kiểu> rõ ràng. Đây là lý do mọi nơi trong STL bạn thấy std::vector<double> — chính là template class, double là "chỗ trống T" được điền.

⚠️ Quy tắc "template nằm trong header"

Template KHÔNG được tách thành file .cpp riêng như class thường. Vì sao? Compiler cần nhìn thấy toàn bộ thân hàm tại thời điểm bạn gọi (để "điền T" và tạo bản). Nếu để trong .cpp, file main chỉ include header — header chỉ có khai báo, không có thân → lỗi link.

Quy ước thực tế: ghi cả định nghĩa template ngay trong .h, hoặc trong file .hpp (header riêng cho template). Đọc code thư viện như Eigen, CasADi sẽ thấy rõ.

5.3 — Lambda: bắt đầu từ "nỗi đau"

🔎 Vấn đề trước khi có lambda

Bạn muốn dùng std::count_if (Phần 4) để đếm mẫu sai số vượt ngưỡng. count_if cần một hàm "điều kiện" — trả về true/false cho từng phần tử. Trước C++11 bạn phải viết hẳn một hàm có tên:

bool is_outlier(double e) { return std::abs(e) > 0.4; }

// rồi truyền tên hàm vào:
int n = std::count_if(err.begin(), err.end(), is_outlier);

Hàm này chỉ dùng đúng 1 lần, ngay tại chỗ này. Viết hẳn một hàm + đặt tên + để ở một chỗ khác trong file thật bất tiện, nhất là khi "ngưỡng 0.4" là biến cần thay đổi.

Lambda = hàm không tên, viết ngay tại chỗ dùng, "vứt đi" sau khi xong. Giống bạn cần một chiếc búa: không đi mua hẳn về cất kho, mà mượn ngay tại chỗ cái búa đặt cạnh.

📌 Cú pháp lambda — mổ xẻ từng dấu ngoặc 
auto f = [](double e) -> bool { return std::abs(e) > 0.4; };
         ▲            ▲       ▲
         │            │       └── thân hàm, như mọi hàm thường
         │            └────────── kiểu trả về (có thể bỏ nếu tự suy được)
         └─────────────────────── "capture": ngoặc vuông, mới chỉ rỗng

Chia làm 4 phần:

  • [] — ngoặc vuông gọi là capture clause. Nó khai báo "tôi muốn mượn những biến bên ngoài nào". Để trống = không mượn gì. (Xem chi tiết 5.4.)
  • (double e) — tham số, y như hàm thường.
  • -> bool — kiểu trả về. Với lambda ngắn, compiler tự suy được, nên ghi hay không đều được. Khuyến nghị: ghi ra cho rõ, nhất là khi mới học.
  • { ... } — thân hàm.

Toàn bộ khối đó gán cho auto f — tức là f trở thành "một thứ gọi được" như hàm:

double e = 0.9;
if (f(e)) { /* ... */ }      // gọi f như gọi hàm thường

Lưu ý dấu chấm phẩy: auto f = ... ; — lambda là một giá trị (đối tượng), nên gán xong phải có ; như mọi khai báo biến.

📌 Ví dụ tối giản nhất — từng bước dựng lên

Bước 1: viết hàm thường trước cho dễ hình dung:

double linear(double x) { return -2.0 * x; }

Bước 2: xóa tên hàm, chèn [] phía trước, gán cho biến:

auto linear = [](double x) { return -2.0 * x; };

Bước 3: dùng. Cách gọi giống hệt:

double u1 = linear(0.5);          // u1 = -1.0
double u2 = linear(2.0);          // u2 = -4.0

Chính là luật điều khiển $u = -kx$ viết gọn. Hãy tự gõ 3 bước này trước khi đọc tiếp — cảm giác "à thì ra là hàm bỏ tên" rất quan trọng.

5.4 — Capture: khi lambda cần "mượn" biến bên ngoài

📌 Vấn đề: lambda đứng một mình, không thấy biến ngoài

Lambda là một đối tượng riêng biệt — nó không tự nhìn thấy biến cục bộ bên ngoài. Muốn dùng k, threshold, alpha... phải xin phép qua capture []:

double k = 2.0;
// ❌ SAI — k ở ngoài, lambda không thấy:
auto bad = [](double x) { return -k * x; };   // lỗi biên dịch

// ✅ ĐÚNG — "chụp" k vào lambda:
auto good = [k](double x) { return -k * x; };  // k được "bắt" theo giá trị

Capture theo giá trị ([k]) = chụp một bản sao của k ngay lúc tạo lambda. Cách hiểu tốt nhất: compiler tự sinh một biến thành viên bên trong đối tượng lambda và copy k vào đó lúc khởi tạo. Như vậy:

double k = 2.0;
auto f = [k](double x) { return -k * x; };   // f giữ bản sao k == 2.0
k = 100.0;                                   // k ngoài đổi
// f vẫn dùng 2.0 — vì f có "bản sao" riêng, không liên quan k ngoài

Ngược lại, capture theo tham chiếu ([&k]) = lambda giữ "địa chỉ" của k ngoài, luôn nhìn thấy giá trị hiện tại:

double k = 2.0;
auto f = [&k](double x) { return -k * x; };  // f nhìn k qua tham chiếu
k = 100.0;                                   // k ngoài đổi
// f bây giờ dùng 100.0 — vì nó "nhìn" chính biến k đó

Cách nhớ bằng tiếng Việt: [k] là "chụp ảnh" (đông cứng giá trị lúc chụp), [&k] là "nhìn qua cửa sổ" (thấy giá trị bất cứ lúc nào).

📌 Các dạng capture — tóm tắt 1 bảng
Cú phápNghĩaDùng khi
[]Không mượn gìLambda độc lập, không cần biến ngoài
[k]Mượn riêng k, theo giá trị (bản sao)Chỉ đọc k, muốn "đông cứng"

Khuyến nghị khi mới học: luôn liệt kê rõ từng biến ([k, threshold]) thay vì vội dùng [=]/[&]. Code rõ ràng hơn, và tránh được bug "mượn quá tay" ở 5.5.

⚠️ Bug kinh điển: mượn tham chiếu [&] trong vòng lặp

Ví dụ sau in ra 3 3 3 thay vì 0 1 2 — hãy tự chạy:

std::vector<std::function<int()>> fs;
for (int i = 0; i < 3; ++i) {
    fs.push_back([&]() { return i; });   // [&] = nhìn biến i qua cửa sổ
}
for (auto& f : fs) std::cout << f() << " ";   // 3 3 3

Giải thích từng bước: cả 3 lambda đều "nhìn" cùng một biến i (vì là tham chiếu). Vòng lặp kết thúc lúc i == 3. Khi gọi f() sau đó, cả 3 cùng nhìn thấy giá trị hiện tại của i = 3. Chúng không hề giữ giá trị 0,1,2.

Sửa: đổi thành [i] — mỗi vòng lặp chụp một bản sao riêng tại thời điểm tạo:

fs.push_back([i]() { return i; });   // 3 bản sao riêng: 0, 1, 2 → in 0 1 2

Trong ROS2, bạn hay gán lambda làm callback trong vòng lặp đăng ký nhiều subscription — đây chính là lỗi "tất cả callback nhận giá trị cuối" gây đau đầu. Nhớ câu hỏi: lambda này đang "chụp ảnh" hay "nhìn cửa sổ"?

K4 double a=1; auto f=[a](double x){return a+x;}; a=10; f(5) trả về bao nhiêu? Nếu đổi [&a]?
✅ Đáp án

[a]: f chụp a=1 lúc tạo → 1+5 = 6. [&a]: f nhìn a hiện tại = 10 → 10+5 = 15. Đây là 2 khác biệt cốt lõi cần thuộc lòng.

5.5 — Lambda + STL: con dao ghép vào thuật toán

📌 count_if — lúc đầu không dùng lambda

Viết "thủ công" bằng vòng lặp, rồi mới thấy cách lambda ngắn gọn hơn:

// Cách cũ, viết tay (hiểu đã rồi mới gọn):
int cnt = 0;
for (size_t i = 0; i < err.size(); ++i)
    if (std::abs(err[i]) > 0.4) ++cnt;

// Cách STL + lambda:
int cnt2 = std::count_if(err.begin(), err.end(),
                         [](double e) { return std::abs(e) > 0.4; });

Hai cách cho cùng kết quả. Điều thú vị: nếu "ngưỡng" là biến cần đổi, lambda capture giúp không phải viết lại:

double thresh = 0.4;
auto cnt3 = std::count_if(err.begin(), err.end(),
                          [thresh](double e) { return std::abs(e) > thresh; });
thresh = 0.9;   // muốn đếm theo ngưỡng mới → tạo lambda mới, không sửa code
📌 "Erase-remove idiom" — lọc phần tử khỏi vector

Đây là mẹo hay dùng để loại outlier (nhiễu) khỏi dữ liệu cảm biến. Gồm 2 bước, phải đi cặp:

err.erase(                                  // bước 2: xóa phần "rác" ở cuối
    std::remove_if(err.begin(), err.end(),  // bước 1: dồn các phần tử "không bị loại"
                   [thresh](double e){ return std::abs(e) > thresh; }),
    err.end());
  • remove_if dồn các phần tử giữ lại lên đầu, trả về iterator trỏ tới vị trí bắt đầu "rác".
  • erase xóa đoạn "rác" từ đó đến cuối.

Đừng cố nhớ thuộc lòng dòng code — hãy nhớ ý: "dồn rồi cắt". Gõ lại 3 lần, mỗi lần đổi điều kiện, sẽ tự khắc nhớ.

5.6 — std::function: "hộp đựng" hàm gọi được

📌 Vì sao lambda gán được vào std::function

Lambda là một đối tượng — nên nó có thể được lưu vào biến, truyền đi, gán lại như mọi giá trị. std::function<double(double)> là cái "hộp" có quy cách rõ: "đựng thứ nào nhận 1 double trả về 1 double".

#include <functional>

std::function<double(double)> controller;      // hộp rỗng, quy cách rõ ràng

controller = [](double x) { return -2.0 * x; };          // nhét lambda LQR vào
double u1 = controller(0.5);                             // -1.0

controller = [](double x) { return -5.0 * x; };          // thay bằng lambda khác
double u2 = controller(0.5);                             // -2.5

Đọc std::function<double(double)> như "biến kiểu hàm": kiểu trả về double, tham số double. Đây chính là kiểu mà ROS2 dùng cho callback: khi tạo subscription, bạn đưa một lambda hoặc hàm — nó được cất trong một std::function và gọi lại mỗi khi có message.

Phân biệt với template (tổng kết nhỏ): std::function là "hộp đựng hàm", còn template là "khuôn sinh ra code theo kiểu". Chúng khác bản chất: hộp đựng = giá trị runtime; template = cơ chế biên dịch.

🔎 Ẩn dụ gói lại toàn phần

Template = khuôn bánh (một khuôn, nhiều loại bột). Lambda = mượn búa tại chỗ thay vì mua về cất kho. Capture = xin phép "chụp ảnh biến" hay "nhìn qua cửa sổ biến". std::function = hộp giấy ghi sẵn "đựng đồ nhận double trả double", bạn nhét lambda nào cũng vừa.

⚠️ Nhầm lẫn hay gặp: capture theo giá trị là "ảnh chụp"

Lặp lại lần cuối cho chắc: [k] chụp giá trị của k tại thời điểm tạo lambda. Nếu k đổi sau đó, lambda vẫn dùng giá trị cũ. Muốn nhìn giá trị hiện tại → bắt theo tham chiếu [&k]. Lỗi này gây ra những bug cổ điển "sao nó không đổi" trong vòng lặp.

💪 Luyện tập Phần 5 — Template & Lambda

BT5.1 Gõ hàm template clamp — giới hạn giá trị trong đoạn [lo, hi] — rồi dùng với cả double lẫn int: 
#include <iostream>

template <typename T>
T clamp(T v, T lo, T hi) {
    if (v < lo) return lo;
    if (v > hi) return hi;
    return v;
}

int main() {
    std::cout << clamp(12.0, -5.0, 5.0) << "\n";  // 5
    std::cout << clamp(-100, -10, 10)  << "\n";  // -10
    return 0;
}
✅ Đáp án

In 5 và -10. Cùng một clamp chạy cho double lẫn int — compiler tự tạo 2 bản riêng. Lưu ý cả 3 tham số cùng kiểu T — clamp(12.0, -5, 5.0) sẽ lỗi vì trộn double/int; hãy thử để đọc thông điệp lỗi template (đọc dòng cuối cùng của lỗi).

BT5.2 Gõ: dùng lambda + std::count_if đếm trong vector xem có bao nhiêu giá trị vượt ngưỡng 0.4, rồi dùng lambda khác + std::remove_if để loại chúng: 
#include <iostream>
#include <vector>
#include <algorithm>
#include <cmath>

int main() {
    std::vector<double> err{0.3, -0.6, 0.5, -0.2, 0.7};
    double thresh = 0.4;
    auto over = std::count_if(err.begin(), err.end(),
                              [thresh](double e) { return std::abs(e) > thresh; });
    std::cout << "so mau vuot nguong: " << over << "\n";  // 3

    err.erase(std::remove_if(err.begin(), err.end(),
                             [thresh](double e) { return std::abs(e) > thresh; }),
              err.end());
    std::cout << "con lai: " << err.size() << "\n";       // 2
    return 0;
}
✅ Đáp án

In so mau vuot nguong: 3 (0.6, 0.5, 0.7) rồi con lai: 2 (0.3, -0.2). Chú ý lambda capture [thresh] — đổi ngưỡng chỉ cần sửa biến ở đầu main. Kỹ thuật erase + remove_if gọi là "erase-remove idiom" — nhớ cặp đôi "dồn rồi cắt" vì code thật lọc dữ liệu bẩn từ cảm biến rất hay dùng.

BT5.3 Gõ lỗi kinh điển capture: vòng lặp tạo 3 lambda bắt theo tham chiếu rồi gọi sau — đoán output, chạy, rồi sửa bằng cách bắt theo giá trị:

#include <iostream>
template <typename T>
class LowPass {
    T alpha_;
    T y_{};
public:
    LowPass(T a) : alpha_(a) {}

};
int main() {
    LowPass<double> lp(0.2);
    double y = 0.0;
    for (double x = 1.0; x < 6.0; x += 1.0) {

}

6.1 — Toán nền: tại sao lại làm đúng các bước này?

📐 Hệ thống & bài toán LQR

Hệ động học bậc nhất: $\dot{x} = 2x + u$. Con số $A=2 > 0$ nghĩa là hệ không ổn định mở vòng (x tự phát triển theo mũ) — đây là "hệ đốt nóng": nếu không điều khiển, nhiệt độ chạy trốn. Ta phải dùng $u$ để giữ x về 0.

Chi phí: $J = \int_0^\infty (3x^2 + u^2)\,dt$, tức $Q=3$, $R=1$. Ý nghĩa của Q và R:

  • $Q$ "đắt" cho việc trạng thái x còn lớn → bộ điều khiển phải dập tắt x nhanh.
  • $R$ "đắt" cho việc dùng u nhiều → bộ điều khiển không được "đạp ga" mạnh.
  • Tỉ số $Q/R = 3$: trạng thái quan trọng gấp 3 lần năng lượng điều khiển → chọn trung dung.

LQR tìm luật $u = -Kx$ tối ưu. Muốn tìm K phải giải phương trình Riccati đại số (ARE):

$$A^T P + P A - P B R^{-1} B^T P + Q = 0$$

Với hệ vô hướng $A=2$, $B=1$: $2AP + Q - \frac{P^2B^2}{R} = 0$ → $4P + 3 - P^2 = 0$.

📌 Tại sao lại là phương trình bậc 2? Và lấy nghiệm nào?

Vì $P$ xuất hiện cả ở bậc 1 ($4P$) lẫn bậc 2 ($P^2$). Nghiệm: $P = \frac{4 \pm \sqrt{16+12}}{2} = \frac{4 \pm \sqrt{28}}{2} = 2 \pm \sqrt{7}$.

  • $P = 2 - \sqrt{7} \approx -0.646$ — âm, loại (P phải xác định dương, vì là "chi phí tương đương" của trạng thái).
  • $P = 2 + \sqrt{7} \approx 4.646$ — dương, chọn.

Tại sao P phải dương? Vì về bản chất $P$ là nghiệm của bài toán chi phí: $J^* = x^T P x$ là chi phí tối ưu còn lại. Chi phí không thể âm. Quy tắc chung: luôn lấy nghiệm xác định dương (P > 0).

Khi có P, gain: $K = \frac{P B}{R} = P \approx 4.646$. Luật điều khiển: $u = -Kx$. Dấu trừ là cốt lõi — feedback âm (xem BT6.3 nếu cần thử nghiệm phá hệ).

📌 Tại sao phải rời rạc hóa bằng Euler?

Hệ gốc là liên tục $\dot{x} = 2x+u$. Máy tính không chạy liên tục — nó tính theo chu kỳ mẫu $T_s$ (10ms trong bài). Mỗi bước, nó giả định $x$ và $u$ không đổi trong 1 khoảng $T_s$ rồi cập nhật:

$$x_{k+1} = x_k + T_s(2x_k + u_k)$$

Đây chính là công thức Euler tiến. Tại sao dùng nó? Vì dễ hiểu, dễ code, đủ chính xác khi $T_s$ nhỏ. Nhưng Euler là xấp xỉ — sai số tỉ lệ với $T_s$. Khi nào đủ nhỏ? Khi $T_s$ nhỏ hơn hẳn hằng số thời gian của hệ (ở đây cực vòng kín $A_{cl} = -2.646$ → hằng số thời gian ~0.38s → $T_s=0.01s$ nhỏ hơn 38 lần, chấp nhận được).

Bài học để đời: trong mô phỏng real-time (F1TENTH, xe tự hành), bạn LUÔN phải quyết định $T_s$ và hiểu sai số rời rạc — đây là thứ nhà tuyển dụng hay hỏi.

6.2 — Cấu trúc chương trình: tại sao bố cục như vậy?

🔎 Nhìn tổng thể trước: chương trình có 4 vai

Hãy tưởng tượng dây chuyền sản xuất 4 công đoạn, mỗi công đoạn độc lập:

  1. Tính toán: giải ARE → ra K (làm 1 lần, trước vòng lặp).
  2. Mô phỏng: lặp N bước Euler, tích lũy kết quả vào vector.
  3. Xuất dữ liệu: ghi toàn bộ ra CSV để Python vẽ.
  4. Báo cáo: in thống kê ra console.

Tại sao phải tách 4 vai? Vì nếu trộn hết vào 1 vòng lặp thì sau này: muốn đổi T_s phải sửa chỗ này, muốn đổi Q phải sửa chỗ kia, muốn xuất JSON thay CSV phải đập đi xây lại. Tách rời = mỗi thứ đổi được độc lập. Đây là nguyên tắc separation of concerns — nền tảng của code chuyên nghiệp.

📌 Tại sao dùng const cho mọi hằng số?

Trong main, các giá trị A, B, Q, R, Ts, T_end đều là hằng số thiết kế — không đổi trong suốt chương trình. Khai báo const:

  • Chống sửa nhầm: compiler báo lỗi nếu vô tình gán lại — bắt lỗi ngay lúc biên dịch.
  • Tự tài liệu hóa: người đọc biết ngay "đây là tham số, không phải biến tạm".
  • Tối ưu: compiler có thể cất hằng vào thanh ghi.

Thói quen đúng: biến nào không đổi thì khai const ngay từ đầu. Code thực tế (ROS2, Autoware) tuân thủ nghiêm ngặt điều này.

📌 Tại sao dùng std::vector + reserve? 
std::vector<double> time, state, input;
time.reserve(N); state.reserve(N); input.reserve(N);
  • Tại sao vector? Vì số lượng mẫu N chưa biết lúc code (nó = T_end / Ts), và ta cần giữ hết lịch sử để xuất CSV sau. Mảng tĩnh `double t[1000]` cố định là bẫy: nếu đổi T_end/Ts sẽ tràn.
  • Tại sao reserve? Vì push_back mỗi lần có thể phải cấp lại vùng nhớ (khi vector đầy, nó nhân đôi kích thước). Cấp lại = copy toàn bộ dữ liệu cũ = chậm. reserve(N) báo trước "tôi cần chừng này chỗ" → cấp 1 lần, không phải copy dư. Trong vòng lặp 100Hz chạy liên tục, đây là cách tránh giật (jitter).
📌 Tại sao tách solve_are thành hàm riêng?

Thay vì viết thẳng công thức vào main, ta gói trong hàm solve_are(A, B, Q, R):

  • Tái sử dụng: sau này cần LQR cho hệ khác (khác A, B, Q, R) chỉ cần gọi lại với tham số mới — không sửa code.
  • Kiểm thử dễ: gọi riêng hàm này để xác nhận ra P đúng trước khi ráp vào mô phỏng (chính là BT6.1).
  • Trách nhiệm rõ: main không phải "hiểu toán", chỉ cần "dùng kết quả".

Quy tắc chung: nếu một khối tính toán dài hơn 3 dòng và dùng cho một ý, hãy gói thành hàm. Code dài mà không tách hàm là dấu hiệu thiếu chuyên nghiệp.

📌 Tại sao dùng lambda cho luật điều khiển? 
const auto control = [K](double x){ return -K * x; };

Luật $u = -Kx$ chỉ dùng trong mô phỏng, không cần là hàm toàn cục. Lambda để ngay tại chỗ, capture [K]:

  • Tại sao capture [K]? K là hằng số tính từ ARE — lambda "chụp ảnh" K lúc tạo. Sau này nếu đổi K bằng biến khác, lambda vẫn dùng K cũ (vô tình đúng ở đây).
  • Lợi ích: đổi luật điều khiển (sang phi tuyến, sang bang-bang) chỉ cần sửa 1 dòng lambda — không đụng vòng lặp. Đây là cách code thật cho phép "cắm" bộ điều khiển khác nhau.
  • const? Lambda không sửa gì ngoài đọc K → khai const để compiler kiểm tra giúp.
📌 Tại sao xuất CSV thay vì in ra màn hình?

CSV là "chợ chung" cho mọi ngôn ngữ: Python, Matlab, Excel đều đọc được. Khi in ra console, dữ liệu mất sau khi đóng terminal; khi ghi file, bạn giữ được để vẽ lại nhiều lần, so sánh các lần chạy khác nhau. CSV = dữ liệu sống lâu dài.

  • Header dòng đầu t,x,u,x_ref: để Python biết cột nào là gì — không đoán.
  • Mỗi mẫu 1 dòng, tách bằng dấu phẩy: quy ước chuẩn, không bàn cãi.
  • 4 cột dù chỉ cần 3: giữ sẵn cột x_ref (giá trị đặt) để sau này vẽ so sánh với x — file "chung hơn", sẵn sàng cho việc mở rộng.

6.3 — Toàn bộ code mẫu, kèm chú thích WHY theo từng dòng

✅ lqr_sim.cpp — tự gõ lại, đọc kỹ từng chú thích 
// ===== BƯỚC 0: THƯ VIỆN =====
#include <iostream>   // cout — in ra màn hình
#include <fstream>    // ofstream — ghi file (xuất CSV)
#include <cmath>      // sqrt — giải ARE
#include <vector>     // vector — lưu lịch sử mô phỏng
#include <algorithm>  // minmax_element — thống kê (Phần 4)

// ===== BƯỚC 1: GIẢI ARE =====
// Hàm trả về nghiệm P dương của A^T P + P A - P B R^{-1} B^T P + Q = 0
// với A, B, Q, R là SỐ THỰC (hệ bậc nhất). Vì sao viết thành hàm riêng:
//   → tái sử dụng cho hệ khác, kiểm thử riêng được, main gọn.
double solve_are(double A, double B, double Q, double R) {
    // Công thức nghiệm: từ 2*A*P + Q - P^2*B^2/R = 0
    //   → P^2*B^2 - 2*A*P*R - Q*R = 0  (nhân cả 2 vế cho -R)
    //   → P = (2*A*R + sqrt((2*A*R)^2 + 4*Q*B^2*R)) / (2*B^2)   [nghiệm dương]
    // Lấy DẤU CỘNG vì nghiệm dương là nghiệm xác định dương (xem 6.1).
    const double disc = 2.0 * A * R + std::sqrt((2.0*A*R)*(2.0*A*R) + 4.0*Q*B*B*R);
    return disc / (2.0 * B * B);
}

int main() {
    // ===== THAM SỐ HỆ & BỘ ĐIỀU KHIỂN =====
    // const: không đổi trong chương trình → chống sửa nhầm + tự tài liệu
    const double A = 2.0, B = 1.0, Q = 3.0, R = 1.0;   // hệ & chi phí
    const double P = solve_are(A, B, Q, R);            // nghiệm ARE
    const double K = P * B / R;                        // gain LQR = PB/R
    const double Ts = 0.01;                            // chu kỳ mẫu 10ms
    const double T_end = 2.0;                          // mô phỏng 2 giây
    const int    N = static_cast<int>(T_end / Ts);     // số bước = 200

    // ===== BƯỚC 2: MÔ PHỎNG =====
    // vector lưu lịch sử; reserve tránh cấp lại bộ nhớ lặp (tại sao? xem 6.2)
    double x = 1.0;                    // trạng thái ban đầu
    std::vector<double> time, state, input;
    time.reserve(N + 1); state.reserve(N + 1); input.reserve(N + 1);

    // Luật điều khiển dưới dạng lambda — tại sao? xem 6.2
    const auto control = [K](double x) { return -K * x; };

    for (int i = 0; i <= N; ++i) {     // i từ 0..N: đủ N+1 mẫu, CÓ mẫu t=0
        const double t = i * Ts;       // thời điểm hiện tại (giây)
        const double u = control(x);   // tính u từ trạng thái HIỆN TẠI
        time.push_back(t);             // lưu TRƯỚC khi cập nhật x
        state.push_back(x);            // lưu x tại mẫu này (chưa đổi)
        input.push_back(u);            // lưu u tại mẫu này
        x += Ts * (A * x + B * u);     // Euler: cập nhật x cho mẫu kế tiếp
    }
    // Vì sao phải lưu TRƯỚC khi cập nhật? → để mẫu (t, x, u) là "ảnh chụp"
    // tại đúng thời điểm t; nếu cập nhật x rồi mới lưu thì dòng CSV bị lệch.

    // ===== BƯỚC 3: XUẤT CSV =====
    // ofstream ghi file; header dòng đầu cho Python biết cột (6.2)
    std::ofstream file("lqr_sim.csv");
    file << "t,x,u,x_ref\n";          // x_ref = 0.0 (giữ mục tiêu về 0)
    for (int i = 0; i <= N; ++i) {
        file << time[i] << "," << state[i] << ","
             << input[i] << ",0.0\n";
    }

    // ===== BƯỚC 4: THỐNG KÊ =====
    // minmax_element trả về cặp iterator (Phần 4) → phải dereference bằng *
    const auto [xmin, xmax] = std::minmax_element(state.begin(), state.end());
    std::cout << "P = " << P << ", K = " << K << "\n"
              << "x min/max: " << *xmin << " / " << *xmax << "\n"
              << "CSV saved: lqr_sim.csv\n";
    return 0;   // trả về 0 = chạy thành công (chuẩn hệ điều hành)
}

Chạy và kiểm tra:

g++ -std=c++17 -Wall -O2 -o lqr_sim lqr_sim.cpp
./lqr_sim            # in ra P=4.64575, K=4.64575, x giảm dần về 0
head -5 lqr_sim.csv  # xem 5 dòng đầu

Kết quả mong đợi: $P \approx 4.646$, $K \approx 4.646$, và $x$ suy giảm từ 1 về gần 0 theo hàm mũ $e^{-2.646t}$ — vì cực vòng kín $A_{cl} = A - BK = 2 - 4.646 = -2.646$.

⚠️ Tại sao cực vòng kín lại là $A_{cl} = A - BK$?

Thay $u = -Kx$ vào hệ: $\dot{x} = Ax + Bu = Ax + B(-Kx) = (A - BK)x$. Hệ số mới là $A_{cl} = A - BK$. Điều kiện ổn định: $A_{cl} < 0$ (nghĩa là x suy giảm theo mũ, không bùng nổ). LQR đảm bảo điều này vì chọn $K$ từ nghiệm ARE dương — nếu dấu sai, $A_{cl} > 0$ và hệ phát nổ (thử ở BT6.3).

6.4 — Vẽ so sánh với Python: tại sao phải làm bước này?

📌 Đây không phải bước phụ — đây là cách CHỨNG MINH code của bạn đúng

Một mô phỏng không ai kiểm chứng chỉ là "code chạy được". Có nghiệm lý thuyết chính xác $x(t) = x_0 e^{(A-BK)t}$ — so sánh kết quả số (Euler) với nghiệm này: nếu chúng khớp, phép rời rạc đúng, LQR đúng, CSV đúng. Kỹ năng này gọi là verification — JD VinFast nhắc đến "quantify uncertainty"; mọi kỹ sư control giỏi đều tự kiểm chứng code mình trước khi tin tưởng.

import csv
import math

t, x, u = [], [], []

Cách đọc kết quả:

  • Hai đường trùng nhau → Euler với $T_s=0.01$ đủ chính xác.
  • Giảm Ts xuống 0.001 → hai đường càng khít (Euler chính xác hơn).
  • Tăng Ts lên 0.5 → đường C++ lệch rõ (Euler là xấp xỉ!).

Bài học: luôn có một "nghiệm chuẩn" để đối chiếu. Trong AV thật, nghiệm chuẩn có thể là mô hình Gazebo, dữ liệu GT (ground truth), hay nghiệm giải tích — nhưng nguyên tắc giống hệt.

6.5 — Lỗi thường gặp (và tại sao chúng xảy ra)

⚠️ Danh sách lỗi kinh điển — nhận biết, hiểu nguồn gốc, tránh
  • Lưu dữ liệu sau khi cập nhật x → các cột lệch nhau 1 bước, đường vẽ bị "trễ" và vặn vẹo. Nguồn gốc: hiểu sai thứ tự "chụp ảnh trước, thay áo sau".
  • Vòng lặp for i < N (thiếu mẫu cuối) → file chỉ có 200 dòng thay vì 201, mất mẫu t=2.0. Vì sao đúng phải là i <= N: ta muốn cả mẫu đầu (t=0) lẫn mẫu cuối (t=T_end).
  • Dùng float thay double → sai số làm tròn tích lũy qua 200 bước, đường mô phỏng lệch dần khỏi analytic. Nguồn gốc: nghĩ "khác gì đâu"; thực ra $10^{-7}$ sai mỗi bước nhân 200 lần + khuếch đại của hệ.
  • CSV thiếu header hoặc thiếu cột → Python đọc nhầm cột, vẽ ra thứ vô nghĩa. Nguồn gốc: tiết kiệm 1 dòng; chính dòng đó là "hợp đồng" với script vẽ.
  • Không mở file kiểm tra nội dung → không biết CSV rỗng/vô nghĩa. Quy tắc: mỗi lần xuất dữ liệu, mở xem 5 dòng đầu trước khi vẽ.
  • Biến không const → sau này vô tình gán lại A, Q... tạo ra "hệ khác" mà không nhận ra. Nguồn gốc: không hình thành thói quen const ngay từ đầu.

6.6 — Mở rộng theo 4 hướng (sau khi chạy được bài gốc)

🚀 Các bước nâng cấp, từ dễ đến khó
  • 1. Gói thành class LQRSystem — tách các thành viên (A, B, K, Ts) và phương thức (compute, step, log). Tại sao: áp dụng đúng OOP đã học (Phần 2); đối tượng tự quản lý trạng thái nội bộ, code gọn và tái dùng được cho nhiều hệ.
  • 2. Thêm bão hòa (saturation) $u \in [-3, 3]$ — cắt u sau khi tính, rồi so sánh đáp ứng có/không cắt. Tại sao: mọi actuator thật đều bão hòa; đây là cửa ngõ vào anti-windup (đã nói trong tài liệu PID). Dùng chính lambda [K, u_max] để minh họa capture nhiều biến.
  • 3. Nâng lên hệ bậc 2 (mass-spring-damper) — state thành vector $[x, v]^T$, A, B, K thành ma trận 2×2. Tại sao: chuẩn bị cho LQR thật nhiều biến; đây là cột mốc quan trọng khi phỏng vấn (LQR bậc 2 là câu kinh điển).
  • 4. Dùng CMake thay g++ tay — tạo CMakeLists.txt: cmake_minimum_required(VERSION 3.16) + project(lqr) + add_executable(lqr_sim lqr_sim.cpp). Tại sao: dự án AV thật (ROS2, Autoware) đều build bằng CMake — học sớm để khỏi "sốc" khi vào codebase lớn.

💪 Luyện tập Phần 6 — 3 bước nhỏ trước khi làm bài lớn

BT6.1 Gõ riêng 3 hàm nhỏ rồi test từng cái trước khi ghép vào chương trình LQR hoàn chỉnh. Tại sao làm thế này? Vì test từng mảnh riêng dễ tìm lỗi hơn là test cả khối 80 dòng — mỗi lỗi biết chắc nằm ở hàm nào. 
#include <iostream>
#include <fstream>
#include <cmath>

// 1) nghiệm ARE hệ bậc nhất: 4P + 3 - P^2 = 0  (A=2, B=1, Q=3, R=1)
double solve_are() {
    // nghiệm dương của P^2 - 4P - 3 = 0  =>  P = 2 + sqrt(7)
    return 2.0 + std::sqrt(7.0);
}

// 2) một bước Euler rời rạc
double euler_step(double x, double u, double ts) {
    return x + ts * (2.0 * x + u);
}

// 3) ghi 1 dòng CSV
void write_csv(const char* path, double t, double x, double u) {
    std::ofstream f(path, std::ios::app);   // append
    f << t << "," << x << "," << u << ",0.0\n";
}

int main() {
    double P = solve_are();
    double K = P;                     // K = PB/R = P
    std::cout << "K = " << K << "\n";  // ~4.64575

    double x = 1.0, ts = 0.01;
    for (int i = 0; i <= 200; ++i) {
        double u = -K * x;
        write_csv("lqr_sim.csv", i * ts, x, u);
        x = euler_step(x, u, ts);
    }
    std::cout << "x cuoi = " << x << "\n";  // gần 0
    return 0;
}
✅ Đáp án

Chạy được: K = 4.64575, x cuoi rất nhỏ (≈$10^{-6}$), file lqr_sim.csv có 201 dòng. Điểm quan trọng: code trả về giá trị, không in lung tung giữa hàm tính — tách biệt "tính toán" và "ghi log". Cấu trúc này đúng chuẩn để sau này ghép vào lớp lớn.

BT6.2 Mở file CSV bằng Python vẽ, rồi sửa hệ số Q từ 3 lên 30 trong solve_are, chạy lại, so sánh: đáp ứng nhanh hơn hay chậm hơn? Vì sao?
✅ Đáp án

Với Q=30: $4P + 30 - P^2 = 0$ → $P = 2 + \sqrt{34} \approx 7.83$, K≈7.83, cực vòng kín $2-7.83 = -5.83$ — x suy giảm nhanh hơn. Vì Q lớn nghĩa là "đắt" nếu trạng thái x còn lớn → bộ điều khiển hành động mạnh hơn. Đổi R từ 1 lên 10 thì ngược lại (u đắt → bám chậm, u nhỏ). Đây chính là ý nghĩa trực giác của trọng số LQR — nhớ kỹ cho phỏng vấn.

BT6.3 Thử phá vòng ổn định: đổi luật điều khiển thành u = +K*x (sai dấu). Chạy, quan sát x tăng không kiểm soát, và nhớ vì sao dấu trừ của feedback là bắt buộc.
✅ Đáp án

Với u = +K*x: x nhân thêm lượng dương mỗi bước → bùng nổ, CSV chứa số khổng lồ/nan. Đó là phản hồi dương (positive feedback) — hệ không ổn định. Bài học: dấu của luật điều khiển phản hồi quyết định ổn định hay không; LQR luôn cho $u = -Kx$ vì nghiệm ARE đảm bảo $A-BK$ có phần thực âm.

PHẦN 7 — QUIZ & TỔNG KẾT

Tự kiểm tra sau 3 tuần — trả lời bằng lời trước khi xem đáp án

📝 Quiz — Trắc nghiệm cốt lõi

Q1 Vì sao C++ dùng cho tầng planning/control của AV thay vì Python? (2 lý do kỹ thuật)
✅ Đáp án

(1) Real-time/deterministic: không có garbage collector chạy ngầm → độ trễ vòng điều khiển ổn định, có thể dự đoán. (2) Hiệu suất: MPC/NMPC phải giải tối ưu trong vài ms — Python chậm hơn 10–100×. Thêm (3) tiếp cận phần cứng trực tiếp.

Q2 Phân biệt con trỏ, tham chiếu, const reference. Khi nào dùng cái nào khi truyền hàm?
✅ Đáp án

Con trỏ *: lưu địa chỉ, có thể là nullptr, cần * để dereference. Tham chiếu &: bí danh, không bao giờ null, dùng thẳng tên. const reference: đọc dữ liệu lớn không copy. Quy tắc: đọc → const&; sửa → &; "có thể không có" → con trỏ.

Q3 RAII là gì? Vì sao smart pointer unique_ptr không cần delete?
✅ Đáp án

RAII: tài nguyên cấp trong constructor, giải phóng trong destructor; destructor tự chạy khi đối tượng ra khỏi scope. unique_ptr bọc vùng nhớ đó — khi nó bị hủy (ra scope), destructor tự delete đối tượng được quản lý → không thể quên, chống rò rỉ. Đó là lý do không cần delete tay.

Q4 std::vector::at() khác operator[] thế nào, dùng cái nào trong vòng điều khiển?
✅ Đáp án

at() kiểm tra biên và ném exception nếu quá — an toàn nhưng chậm hơn một chút. operator[] không kiểm tra — nhanh, gây undefined behavior nếu quá biên. Trong vòng real-time đã kiểm soát chỉ số: dùng operator[]; khi đọc dữ liệu không tin cậy (ví dụ message ngoài): dùng at().

Q5 Lambda [x] vs [&x] khác nhau bản chất gì? Cho ví dụ lỗi thực tế.
✅ Đáp án

[x] chụp bản sao giá trị x tại thời điểm tạo lambda; đổi x sau đó không ảnh hưởng. [&x] chụp tham chiếu — luôn thấy giá trị hiện tại. Lỗi kinh điển: tạo N lambda trong vòng lặp với [&] rồi gọi sau khi vòng lặp kết thúc → tất cả cùng trỏ về giá trị cuối. Dùng [x] (giá trị) hoặc capture từng biến cụ thể.

Q6 Hệ $\dot{x} = 2x + u$, $Q=3$, $R=1$. Gain LQR $K$ là bao nhiêu và cực vòng kín ở đâu?
✅ Đáp án

ARE: $4P + 3 - P^2 = 0$ → $P = 2+\sqrt{7} \approx 4.646$. $K = PB/R = 4.646$. Cực vòng kín: $A_{cl} = A - BK = 2 - 4.646 = -2.646 < 0$ → ổn định tiệm cận, x suy giảm $e^{-2.646t}$.

🎯 Tổng Kết

  • Vì sao C++: real-time deterministic + hiệu suất + tiếp cận phần cứng — là ngôn ngữ production của AV.
  • Phần 1 — Nền tảng: double cho control, con trỏ (có thể null) vs tham chiếu (không null), const reference là quy tắc vàng khi truyền hàm.
  • Phần 2 — OOP: class + encapsulation + inheritance + virtual/override; destructor virtual là bắt buộc; kế thừa 1 cấp là đủ cho control.
  • Phần 3 — RAII: bộ nhớ tự giải phóng qua destructor; unique_ptr mặc định, shared_ptr chỉ khi chia sẻ, weak_ptr phá vòng tham chiếu.
  • Phần 4 — STL: vector = mảng động, map = tra cứu, algorithm + iterator [begin, end).
  • Phần 5 — Template & Lambda: generic code; lambda capture theo giá trị vs tham chiếu; std::function = callback (nền ROS2).
  • Phần 6 — Dự án: viết lại LQR bằng C++ thuần, xuất CSV, vẽ so sánh analytic — bài tập kiểm chứng rời rạc hóa.
